    Edge Gateway

    CM upgrade to manage Edge Gateway

    1. Log in to cm cli and execute Edge Gateway patch retrieval process.

      parameters:

      • Host: raptor.demo.guardium
      • User: root
      • Path: /opt/guardium_tz_bootcamp_automation/upload/source_files/appliances/extensions/SqlGuard-12.0p15004_Edge_Sep_02_2026.tgz.enc.sig
      • Port: 2223
      • Password: <default service password>

      store system patch install scp
      Monitor the progress as the patch downloads to the appliance, noting that the large file size may require a while to complete. Once the download finishes and the patch appears in the available list, do not initiate the installation from the command line. Because this specific update must be managed via the User Interface (UI) or the API, finish the current cli command by selecting the q option.

    2. Register patch and retrieve information about it (because patch is huge it takes time). 

      show system patch available

    3. From cm UI open Patch Management view. Select the Central Manager 1 and locate the patch 2 that was just uploaded to the system. Trigger the installation process by clicking the Install option 3. Choose the immediate installation 4 and confirm your selection 5 to finalize the task. The system will then schedule the specified patch for deployment

    4. While the patch installation runs in the background, shift your focus to the additional laboratory tasks to maintain workflow efficiency.

    Setup Edge Gateway config on CM

    1. Confirm the installation of patch 15004 from the cm command line. If the installation is still in progress, wait for the process to be completed before proceeding. 

      show system patch installed

    2. Check that feature flag responsible for Edge Gateway is enabled. 

      grdapi list_feature_flags

    3. Access the Central Manager view within the cm UI and select Register Edge Gateway from the Actions dropdown menu.

    4. In the registration window, enter the required information and press Register Edge Gateway button.

      Edge parameters:

      • Edge name: sauropod.demo.guardium (hostname of the machine where the Edge Gateway and Kubernetes cluster are running)
      • Namespace: edge (namespace where Edge Gateway will be deployed)
      • Storage class: local-path (storage class used by the Edge Gateway; it must support RWO mode)
      • Export to: cm.demo.guardium (aggregator for audited events; for this lab, we are using the Central Manager)
      • Version: 2.0.1 (Edge Gateway version to be installed)
      • Use HAProxy for ingress: (Routing between services and the aggregator will be configured via HAProxy; otherwise, manual NodePort configuration may be required)

    5. The Install edge bundle window will appear along with a prompt to save the generated deployment archive. Save the file and confirm that the new appliance now appears in the Central Manager view.

    6. Execute this command to download deployment scripts on sauropod

    7. Unpack downloaded archive tar xvf

    Edge Gateway deployment

    1. The deployment initialization script requires the expect tool on sauropod. dnf -y install expect
    2. Navigate to the directory with the extracted archive and run the edge-install.sh script to initialize the Edge Gateway installation. The script will prompt for the Kubernetes cluster type to be used for the deployment, whether to add the image repository certificates located on the Central Manager, and whether to create the namespace specified earlier during the service definition (select Yes for each of the following prompts). cd /root/sauropod.demo.guardium/

    ./edge-install.sh

    1. After a short while, you should observe a deployment started. kubectl get pods -A

    2. After a while the strimzi operator will be restarted and deployment will be continued. You should soon see on the list the edge_manager pod kubectl get pods -A

    3. After few minutes the Edge Gateway deployment should finish with success. Execute this loop to confirm it (provide you edge-manager pod name). while true; do LINE=$(kubectl logs -n edge | grep "EDGE_SERVICES_INSTALLATION_STATUS is Completed" | tail -n 1); [ -n "$LINE" ] && echo "$LINE" && break; sleep 5; done

    4. Open the Central Manager view in the CM UI and confirm the status change for the Edge Gateway. A green checkmark should now appear, confirming that communication is working correctly.

    5. In the cm UI, create a new dashboard and name it - Edge Gateway. Then, add the following four reports: Edge Buff Usage Monitor, Edge Extraction Log, Edge Live Full SQL, Edge Live Session List. Even though you are not sending any events to the Edge Gateway yet, the Edge Buff Usage Monitor report should show sniffer statistics generated every minute.

    6. The next step is to set the policy. In the cm UI, open the Security Policies view. Select the Log Everything policy, and then select the Install option from the dropdown list. In the window that appears, select just deployed Edge Gateway and the Install and Override option. The execution of the change will be confirmed by an additional message.

    7. In the refreshed view, information about the installation of the new policy should appear.

    Send traffic from STAP to Edge Gateway

    1. In the Central Management view, select the Edge Gateway. This will display a list of ports where the service is listening for specific traffic types. These ports are randomly assigned from the NodePorts pool for each Edge Gateway instance. Make a note of both ports assigned to Unix-TAP, as you will need them for the next configuration step

    2. Open the Setup by Client view and select the ceratops.demo.guardium client. Then, choose the currently installed S-TAP version - 12.2_r120202259_1 - and change the values: WINSTAP_USING_EDGE from 0 to 1 WINSTAP_SQLGUARD_IP to sauropod.demo.guardium WINSTAP_SQLGUARD_PORT to node port identified in point 1 as a Windows S-TAP WINSTAP_SQLGUARD_TLS_PORT to node port identified in point 1 as a Windows S-TAP (TLS)

    3. Confirm the change by monitoring the status of the task.

    4. In the Edge Buff Usage Monitor report (in the Edge Gateway dashboard), the Analyzer Total value should begin to change, indicating the number of events analyzed by the sniffer.

    5. Reports with Edge Live in their name provide a new functionality that allows you to download a fragment of the data currently being processed on the Edge Gateway. This confirms the correct operation of policies without having to wait for the full cycle on the aggregator side. The report is equipped with an additional Edge Gateway Data Refresh option, which enables sending a request to the sniffer. Use this option in the Edge Live Session List report.

    6. After a moment, use the new option again to confirm that the data has been transmitted.

    7. Refresh the report and ensure that the data is flowing to the Edge Gateway and is being properly audited according to the installed policy.

    8. You can also check the Edge Live Full SQL report and notice that SQL’s are logged correctly.

    9. By default, data is synchronized with the aggregator every hour. Depending on the volume of events, this process can be delayed or accelerated. In our laboratory environment, we can change this value to 10 minutes. To do this, select the Edge Gateway in the Central management view and select the Edit edge parameters option from the context menu.

    10. In the Configure edge gateway parameters window, expand the Environments list, which allows for editing individual service parameters. Select data-manager and change the value of the DB_ROTATE_INTERVAL parameter from 3600 to 600, then confirm the change – Update parameters.

    11. From now on, events processed by the Edge Gateway will appear in reports every 10 minutes. Open the standard Full SQL (Training) report in the Training dashboard and confirm that the data is indeed updating according to this schedule.
